# 反例：垂域状态卡片（旅行登机牌）

> **这不是可运行的代码。** 它是从主仓 `feature/travel-card` 分支搬出来的一个实现，
> 保留下来是因为它演示了一个**我们决定不做的方向**，而删掉它会让下一个人重新走一遍。

## 它是什么

一张登机牌样式的状态卡片（计划中 → 值机 → 安检 → 登机 → 起飞 → 到达，六站状态机），
下面挂一个 AI 面板：用户**不打字**，面板读卡片当前状态，直接产出四张子卡
（天气 / 值得去的一个地方 / 必须预订的 / 必须吃的）。

技术上它是真的在推理，不是演示数据：`TravelAgent` 在页面出现时（不是点击时）启动进程内
Node 运行时、开会话、prompt `deepseek-v4-flash`、解析 JSON 回答；按状态缓存，
切换状态只是查缓存，`prepare()` 在后台预取下一个状态。

## 为什么搬出来

主仓的产品身份是 **dsh 的鸿蒙外壳**：一个能跑 dsh 的通用会话界面。
垂域卡片（旅行、饮食、游戏）会把主仓变成"每个场景一套 UI 的应用集合"，
而每条垂域都需要自己的状态模型、自己的渲染、自己的维护者。

判据很简单：**这张卡片能不能被另一个垂域复用？** 登机牌不能。
它上面每一个元素（六站状态机、撕口、机翼徽标）都只为"一次航班"存在。
把它放进外壳，等于让外壳认识"航班"这个概念。

所以：**外壳只提供会话、文件、审批、设置；垂域归各自的仓。**
这个仓库（`Harmony-harness-game`）就是第一个垂域仓。

## 里面有什么

| 路径 | 原本在哪 | 作用 |
|---|---|---|
| `travel/TravelModel.ets` | `entry/src/main/ets/travel/` | 六站状态机 + 数据模型 |
| `travel/TravelAgent.ets` | 同上 | 进程内 Node 运行时 → ACP → 解析 JSON |
| `travel/TravelPrompt.ets` | 同上 | 四张子卡的 prompt 与 schema |
| `view/TravelCard.ets` | `entry/src/main/ets/view/` | 登机牌本体（Canvas 绘制） |
| `view/TravelInsightPanel.ets` | 同上 | 卡片下方的 AI 面板 |
| `pages/TravelDemo.ets` | `entry/src/main/ets/pages/` | 独立 demo 页 |
| `demo/travel-ai-card.html` | `docs/demo/` | 网页版原型 |

要让它重新编译，把文件放回原来的路径，并把 `pages/TravelDemo` 加回
`entry/src/main/resources/base/profile/main_pages.json` 的 `src` 数组，
入口临时改成它即可（原分支用一个 `ENTRY_PAGE` 常量切换）。

## 值得留下的三条经验

即使这个方向不做，这三条结论仍然成立：

1. **卡片必须自己说清"我是什么时候的事实"。** 这个实现里 AI 结果是按状态缓存的，
   所以"3 小时前的天气"和"现在的天气"是两回事——缓存必须带时间戳，否则用户会
   拿旧数据当现状。
2. **降级要标注，不要伪装。** `FALLBACK_INSIGHT` 在运行时报错时仍然给出一段真话，
   并明确标成 fallback，而不是把内置数据说成推理结果。
3. **绘制的数字要量，不要目测。** 机翼徽标第一版是六个点的单条路径，路径折返导致
   填充规则把内部挖空，渲染成一个空心 V；第二版量出 50×69 px（高大于宽，像立着的飞机），
   调到 66×58 px 才是右向机头。这类问题只有量了才知道。

## 不要照抄的地方

- **入口常量化**：为了 demo 把 `ENTRY_PAGE` 从 `pages/Index` 改成 `pages/TravelDemo`，
  这会让 `Index` 整个被绕过。demo 页应该走独立 Ability 或路由，不该改入口。
- **页面出现即启动运行时**：对 demo 是合理的（省一次点击），对正式功能是浪费——
  用户可能只是路过这个页面。应该在首次真正需要时启动。
